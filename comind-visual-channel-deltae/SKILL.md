# 视觉通道强度的 ΔE 量化

「质感不足」「看不清」「四档分档合不合理」这类诉求**看起来是审美，其实可测量**。本技能把
主观 complaint 转成阈值判据，让结论从口味之争变成缺陷指认。

## 核心原则

> **先找仓库内既有可辨门槛作锚点，绝不自造标准。**

自造标准会陷入「多亮才算亮」的主观循环。comind 里的现成锚点：

| 锚点 | 含义 | 亮色实测（base `#FFFFFF`） |
|---|---|---|
| `--surface-muted`（stone-50） | 弱底面板 · 几乎不可见 | ΔE 1.83 / contrast 1.044 |
| `--surface-subtle`（stone-100） | 弱底面板 · **「这层底要能看出来」的门槛** | **ΔE 3.52 / contrast 1.091** |
| `--bg-hover` / `--bg-active` | 交互态底 | 更强 |
| `--bg-base` | 底色通道的比较基准 | — |

暗色（base `#1A1A1E`）：`--surface-muted #1F1F22` ΔE 2.58；`--surface-subtle #2A2A2E` **ΔE 7.79**。

## 第 0 步：先标「性质」，再谈重复

在论证「同一事实重复呈现 / 双呈现」之前，**必须先给每个位置标注性质**：

| 性质 | 形态特征 | 职责 |
|---|---|---|
| **录入面 / 可写入口** | `role="button"` + 占位符（`—`）+ 点击唤起编辑器；形态是表单/属性表 | 引导填写（ADR-0050 D1「挂载即显示」） |
| **展示位 / 只读信号** | 视觉编码（底色、图标、徽章、色条） | 扫描时传达信息 |

⛔ **不变量（如 ADR-0050 D19「单一权威展示位」）约束的是同一事实的两个「展示」源**，
不约束「录入面 + 展示位」—— 后两者职责不同、**不互斥**，不构成重复。

**判别方法**（从代码读，不靠猜）：
- 看有没有 `role="button"` / `@click` 唤起编辑器 / 有无 `—` 占位分支 ⇒ 录入面；
- 只有样式绑定（`:class` / `background`）无交互 ⇒ 展示位。

**同项目正反例**：
- ✅ ADR-0050 D20 删行内 chips 列 —— chips 与下方字段区**都属录入面**、同一职责两个位置 ⇒ 去重成立。
- ⛔ 把底色（展示位）与字段区（录入面）算作「双呈现」⇒ 判据用错轴，结论无效。

⇒ 查仓库里同类「唯一性/去重」决策时，**先确认它约束的到底是展示还是录入**，
别默认两者都算。

## 图标方案：家族感与可分档的拉扯

给枚举型字段（优先级/状态/严重度）选图标时，**两条约束同时成立且互相拉扯**：

| 约束 | 做法 | 失败模式 |
|---|---|---|
| 可分档 | 四档用**不同几何形状** | 家族参差 ⇒ **不叫统一风格** |
| 统一风格 | 四档**同外框**，只变填充度 | 填充度是**连续量** ⇒ 小尺寸必然并档（实测 8px 废） |

⛔ **不要在「形状分档」与「填充度分档」之间二选一** —— 那是假选项。

**正解：找一个「差异可编码在轮廓内部」的统一图元**，使四档轮廓完全相同（严格同一图标），
差异只在内部某一处：

- **象限网格 2×2**（适用于本仓 priority）：轮廓 = 十字轴，差异 = 点亮哪一格。
  额外优势：**位置本身携带语义**（左上=重要且紧急、右上=重要、左下=紧急、右下=都不要），
  读者无需记忆图例。
- 重复次数（1/2/3/4 道斜杠）：家族感够，但位置不携带语义。

### 像素预算决定方案生死

**选图元前先算**：需要的最小笔画数 vs 目标尺寸 ÷ DPR。笔画间距 < 1px 就并档。

实测（24 / 18 / 16 / 12px 四档梯度 + 灰度检验）：

| 画法 | 24px | 18px | 12px | 结论 |
|---|---|---|---|---|
| 2×2 四格填色 | 可辨 | 糊 | 糊 | ✕ 格子内像素不足 |
| 点亮点 + 粗细阶梯 | 可辨 | 糊 | 糊 | ✕ 描边丢失 |
| **十字轴 + 单格实心** | 可辨 | 可辨 | 可辨 | ✓ 轴 2 线 + 点 1 块，最省 |

**「半实」（外框内套一个内点）是设计上失败的中间态** —— 视觉上像外框损坏，
而非有意的第四级。宁可跳到「纯描边 + 尺寸/线宽阶梯」。

### 验收阈值要加「家族相似性」

在 D 类阈值表里补一条：**四档轮廓完全相同，差异仅限轮廓内部**。
否则「可分档达标」会掩盖「风格参差」—— 后者用户未必能量化，但一眼能看出不专业。

### 并存混淆检验

新增行内图标后，必须检验它与**已有行内图标**并排是否混淆。
本仓：priority 十字轴 vs status 圆形轮廓 ⇒ 形态差异明显，安全。
（两枚都是圆/都是描边线框时风险高，需改形或改位。）

### ⛔ Vue：`h()` 包装组件必须展开 attrs，否则颜色/size 全丢

用 `h()` 给同一个组件注入不同默认 prop（而非为每档写一个 SFC）时：

```ts
// ❌ attrs 被丢弃：父组件 :color="x" / :size="n" / @click 全都不进子组件
const wrap = (k) => () => h(Quad, { quadrant: MAP[k] })

// ✅
const wrap = (k) => defineComponent({
  inheritAttrs: false,
  setup(_p, { attrs }) { return () => h(Quad, { ...attrs, quadrant: MAP[k] }) },
})
```

**症状**：图标渲染出来了但**没有对应颜色** —— 子组件收不到 `color`，退回 `currentColor`（文字色），
四档看起来全是同一个颜色。

**判据**：`h()` 的第二个参数是**硬编码 props**，父级传入的 attrs 不会与之合并。
⇒ **凡包装组件，必须显式展开 attrs**。
⇒ **同一文件内两种写法混用时逐个查有没有包装层**（本项目 status 图标是直挂 SFC 所以无此问题，
priority 走 `h()` 包装所以有 —— 同一份色板，两条路径，只有一条坏掉，最容易漏测）。

### 此类「按档位切换图标」的回归测试

直挂组件的既有测试覆盖不到包装层（它测的是 `<Icon name="status-x">`）。须单独钉住：

1. **语义色注入**：逐档断言渲染出的 `stroke` / `fill` 等于期望 token；
2. **档位互不重合**：把「区分档位的那个属性」（此处是点亮点的 `x,y`）取出，断言 `uniq.size === 档数`
   —— 直接对应「四档并档」这个本ADR 的核心风险；
3. **props 透传**：显式传 size / strokeWidth / color，断言落到 svg 上。

写完必须做**回退对照**：把修复点（如 `{...attrs}`）撤掉 ⇒ 该例必须转红，其余仍绿。
否则锁不住东西。

### 数组顺序驱动的网格：改排序 ≠ 改位置

`grid-template-columns: 1fr 1fr` + `v-for` 遍历数组时，**数组顺序直接决定屏幕位置**：
先横后纵展开为 第1项→左上、第 2 项→右上、第 3 项→左下、第 4 项→右下（不是排成一列）。

**改轴向时必须两件事都做**，缺一即错位：
1. **改数组顺序**（= 改位置）；
2. **改每格的 title / 说明文字**（= 改内容）—— 顺序对了但文字没改，四格全部「名不副实」。

**逐格断言脚本**（定案后必跑）：
```
位置 →(是否重要, 是否紧急) 语义表
for (item, pos) in zip(items, ['左上','右上','左下','右下']):
    has_imp = '重要' in title and '不重要' not in title   # 不重要优先匹配
    has_urg = '紧急' in title and '不紧急' not in title
    assert has_imp == 语义[0] and has_urg == 语义[1]
    assert tint == f'var(--priority-{key}-fg)'
```
⚠️ **判定逻辑别用字面 `in`**：`'重要+紧急' in '重要且紧急'` 为 False ⇒ 会误报 4 格全矛盾。
要按「`不重要` 优先匹配」的布尔判定写。

**别信注释，先对照**：本次布局注释里有个错字（「列=不紧急/紧急」写成「不紧急/不紧急」），
让我误以为布局已按正确轴向写好 ⇒ 白改一轮。**改轴向前先核对注释与实际语义**。

**双向同步标注**：同一字段跨两处二维呈现（块行图标 + 矩阵视图）时，**在两处源码各写一句
「改此须同步 XXX」** —— 改代码的人不一定读 ADR。

### ⛔ 轴向必须由既有权威载体决定，不能由排序推导

给「二维语义」（优先级、风险等级、影响面 × 可恢复性…）设计图标/网格时：

1. **先 grep 全仓该字段是否已有「二维呈现」**：另一处视图、矩阵组件、看板分组。
   本例 priority 已有 `QuadrantView` 用 `grid 2×2` 呈现 —— **它的轴向是权威**。
2. **同一字段禁止两种轴向**。块行图标与矩阵视图轴向相反时，用户在两处读到的格位相反，
   比「轴向选错」更糟（选错至少处处一致）。
3. **读 CSS grid 布局必须纸上展开一次**：`grid-template-columns: 1fr 1fr` + 数组顺序
   ⇒ 展开为「先横后纵」= 左上 / 右上 / 左下 / 右下；**不是**上下排一列。
   `for (item of array)` 配 2×2 grid 时最容易误读。
4. **色板与轴向解耦**：颜色 = 档位标识（红=Urgent / 蓝=Medium …），轴向 = 点亮哪一格。
   改轴向不带动色板，否则要同步改 5 处（token / 注册表 / 视图 CSS / tint / 测试断言）。

**全局一致性核查**：定案后 grep 该字段的**所有**语义描述语（`重要` / `紧急` / `不重要` 等），
逐一核对字面与所属档位 —— 遗留的旧读法通常藏在**斜杠命令 alias**、**视图头注释**、
**空值占位说明**里，这些不在主数据源旁边，极易漏。

### ⛔ 工具坑：`python -c` 里的反引号会被 bash 吞掉

改含markdown 反引号的文件时，`python -c "...\`code\`..."` 里的反引号**仍是命令替换** ——
内容被替换成空字符串，bash 报 `X: command not found`，但脚本仍 exit 0。

**修法**：用 `python - << 'PYEOF'` heredoc（单引号 heredoc 不做替换），或用 Edit 工具。
**症状特征**：stderr 出现 command not found 而 exit code 为 0 ⇒ 必须 grep 复核写入结果。

## 执行步骤

### 1. 取值（只读代码，不猜）

- token 定义：`src/styles/tokens/_semantic.scss`（`--bg-base` / `--surface-*` / `--text-*`）、
  `src/styles/tokens/_components.scss`（组件色，如 `--priority-*-bg/fg`）
- 使用处：`src/styles/components/*.scss`
- 亮/暗两套都要取（`[data-theme="dark"]` 是独立一组值，常被漏）

### 2. 写量化脚本（用已装好的 Python）

**必须用** `C:/Users/jay/.workbuddy/binaries/python/envs/imgmeta/Scripts/python.exe`
（已装 PIL 12.3.0）。⛔ managed python 与新建 venv **无网络装不了包**，`pip install` 直接
no matching distribution。脚本落 `outputs/`。

四个必测维度：

| 维度 | 算法 | 阈值 |为什么 |
|---|---|---|---|
| **通道强度** | `ΔE(bg, --bg-base)`（CIE76，JND≈2.3） | ≥ `--surface-subtle` 基准 | 「能不能被看见」 |
| **相邻档并档** | `ΔE(tierA, tierB)` | **≥ 6**（2.5× JND） | 留主题压缩余量 |
| **叠加态衰减** | 叠加态 ΔE 相对基态的衰减率 | **≤ 15%** | 覆盖用户高频操作 |
| **通道数** | 独立感知通道计数 | **≥ 2** | 见下|

对比度用 WCAG 相对亮度比。`color-mix(in srgb, C p%, base)` 按整数通道线性插值即可
（不是 LAB 空间插值，但 p ≤ 26% 时误差可忽略）。

### 3. 判定：分档编码的通道数

「分档」= 区分 N 个等级。**区分两档 ≠ 区分四档**：

- 两档（非黑即白）容易，所有通道都够 ⇒ **「最低档无信号」通常是对的**
  （反例参考：Todoist P4 = 无色）。
- 四档难。若四档用**同族微差**（长度 / 角度 / 像素宽度 / 透明度深浅）分档 ⇒ 小尺寸与色觉
  障碍下必然并档。**这是 Jira 旧图标翻车的直接原因**。

⇒ 铁律：**四档必须在目标尺寸下占不同基本形状/拓扑，而非同族微差。**
⇒ 连续量（透明度、像素宽度）只能表达**存在性**，不能表达**等级**。

### 4. 叠加态衰减不可省

必测：用户点击/激活时叠加的底色会吃掉多少通道信号。

comind 的已知叠加态：`--block-active-bg`、`--selection-bg`、`:hover`、`:active`。
**token 注释里的意图声明不等于实现效果** —— `_components.scss:68-69` 明写「激活 block 的
底色必须弱到不吞掉优先级底色」，实测吞34.8%。**注释断言必须实测复核**。

### 5. 顺带核「定义本身有没有矛盾」

视觉通道不稳定常常是**语义定义打架**的表征。枚举字段（如 `priority` 的
`Low/Medium/High/Urgent`）常有：字段名字面义vs `description` vs 排序 vs 某视图的象限义。
四者不一致时，**图标怎么画都有一档读错** —— 量化色差之前先核这个。

**查 `closedValues` 是否已落库**：已落库则只改展示映射表（label / sortOrder / 图标映射），
**不改值、零迁移**；未落库才可考虑改枚举本身。

## 行业取证（选分档方案时用）

| 产品 | 做法 | 可借鉴 |
|---|---|---|
| **Jira 旧** | 同形状箭头 + 仅颜色不同 | ⚠️ 反面教材，Atlassian 已重设计 |
| **Jira 新** | 形状化 + 方向序列（尾点 / 双头箭头） | 「不靠颜色也得分档」的目标 |
| **Todoist / TickTick** | 同形状配四色 + **P4 无色** | 最低档无信号是对的；靠位置/排序分档 |
| **Asana** | 默认不给优先级上色 | 颜色是强调手段，不是默认编码 |

## 坑

- **别只测基态**。暗色 + 激活态叠加是信号最弱的环境，也是最该测的。
- **别用 DPR 无关的像素宽度当通道**。2px vs 3px 在 DPR 1 下差 1 物理像素 = 无信息；
  DPR 1.5 / 2 下更不可靠。⇒ 这类「装饰性差异」不承载信息，不能当分级依据。
- **`--block-content` 类局部容器只覆盖局部**。改动前确认底色通道覆盖范围（本例不含
  bullet 与status 图标），否则「整行着色」的视觉预期与实际不符。
- **Python 脚本里的类型**：本仓 `hex2rgb` 要同时接受 str 和 tuple（`mix()` 会两种都传），
  写死一种会 `AttributeError`。
- **视觉结论要给证据位置**，不能只给结论 —— 每条判据标注代码行号与 token 名。

## 输出形态

1. 量化表（亮/暗双列，每档列 ΔE / contrast / 叠加衰减率）；
2. 缺陷清单（每条：现象 + 代码位置 + 实测值 + 阈值）；
3. 方案对比（各方案的代价，以及**反证** —— 换个方案能否满足同一目标）；
4. 验收阈值表（可直接落成单测断言）。
