# 超出范围知识库

仓库中的 `.out-of-scope/` 目录存储被拒绝的功能请求的持久记录。它有两个用途：

1. **组织记忆**（institutional memory）——记录功能为何被拒绝，使关闭 issue 后理由不至于丢失
2. **去重**（deduplication）——当新 issue 与既往拒绝匹配时，技能可以引用之前的决策，而不是重新争论一遍

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个。请求同一事物的多个 issue 归入同一个文件。

## 文件格式

文件应以轻松、易读的风格撰写——更像一篇简短的设计文档，而不是数据库条目。使用段落、代码示例和例子，让理由对初次接触的人清晰且有用。

```markdown
# 深色模式

本项目不支持深色模式或面向用户的主题定制。

## 为什么超出范围

渲染管线假定使用 `ThemeConfig` 中定义的单一调色板。支持多主题将需要：

- 一个包裹整个组件树的主题上下文提供者
- 每组件的主题感知样式解析
- 一个用于用户主题偏好的持久化层

这是一项重大的架构变更，与本项目专注于内容创作的定位不符。主题定制是下游嵌入或再分发输出内容的消费者需要关心的事。

```ts
// 当前的 ThemeConfig 接口并不是为运行时切换设计的：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，构建时解析
  fonts: FontStack;
}
```

## 既往请求

- #42 — “添加深色模式支持”
- #87 — “用于无障碍的夜间主题”
- #134 — “深色主题选项”
```

### 命名文件

为概念使用简短、描述性的 kebab-case 名称：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应足够易认，让浏览目录的人不用打开文件就知道拒绝的是什么。

### 撰写理由

理由应当有实质内容——不是“我们不想要这个”，而是为什么。好的理由会引用：

- 项目范围或理念（“本项目专注于 X；主题定制是下游关心的事”）
- 技术约束（“支持它需要 Y，这与我们的 Z 架构冲突”）
- 战略决策（“我们选择用 A 而不是 B，因为……”）

理由应当是持久的。避免引用临时状况（“我们现在太忙了”）——那不是真正的拒绝，只是延期。

## 何时检查 `.out-of-scope/`

分诊期间（步骤 1：收集上下文），读取 `.out-of-scope/` 中的所有文件。评估新 issue 时：

- 检查请求是否匹配某个已有的超出范围概念
- 匹配依据概念相似度，而非关键词——“夜间主题”匹配 `dark-mode.md`
- 如果匹配，向维护者指出：“这与 `.out-of-scope/dark-mode.md` 相似——我们之前因为［理由］拒绝过。你现在还是这么想吗？”

维护者可以：

- **确认** — 把新 issue 追加到现有文件的“既往请求”列表，然后关闭
- **重新考虑** — 删除或更新超出范围文件，该 issue 进入正常分诊流程
- **不同意** — issue 们相关但不同，按正常分诊继续

## 何时写入 `.out-of-scope/`

只有当 **enhancement**（而非 bug）被*拒绝*并标记为 `wontfix` 时。这条规则对 enhancement 类 PR 与 issue 完全相同——被拒绝的 PR 也记录在此，以免同样的请求以新代码的形式卷土重来。

当某事物因**已经实现**而被关闭为 `wontfix` 时，**不要**写入这里。那是已构建的功能，不是被拒绝的；记录它会让去重检查被虚假拒绝污染。此时关闭评论应指出该功能已存在的位置。

流程：

1. 维护者判定某个功能请求超出范围
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 如果有：把新 issue 追加到“既往请求”列表
4. 如果没有：以概念名、决策、理由和首个既往请求创建新文件
5. 在 issue 上发布评论，解释决策并提及 `.out-of-scope/` 文件
6. 给 issue 打上 `wontfix` 标签并关闭

## 更新或移除超出范围文件

如果维护者对先前被拒绝的概念改变了主意：

- 删除该 `.out-of-scope/` 文件
- 技能无需重新打开旧 issue——它们是历史记录
- 触发重新考虑的新 issue 进入正常分诊流程
