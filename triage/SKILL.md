# 分诊

让项目 issue 跟踪器上的 issue 通过一个由分诊角色构成的小型状态机流转。

如果本仓库把外部拉取请求（PR）视为请求入口（见 issue 跟踪器配置），分诊也覆盖它们：**PR 就是附带代码的 issue**——相同的角色、相同的状态、相同的状态机，只有下方标明“针对 PR”的少量差异。对裸写的 `#42`，按跟踪器配置解析为 issue 或 PR。

分诊期间发布到 issue 跟踪器的每条评论或 issue **必须**以下面这行免责声明开头：

```
> *本内容由 AI 在分诊过程中生成。*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md) — 如何撰写持久的代理简报
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) — `.out-of-scope/` 知识库的工作方式

## 角色

两个**类别**（category）角色：

- `bug` — 有东西坏了
- `enhancement` — 新功能或改进

五个**状态**（state）角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者提供更多信息
- `ready-for-agent` — 已完整定义，可供 AFK 代理执行
- `ready-for-human` — 需要人工实现
- `wontfix` — 不予处理

对 PR 而言，同样的状态针对所附代码解读：`ready-for-agent` 表示已附上简报，代理应对 diff 采取下一步；`ready-for-human` 表示已可由人工合并。

每个完成分诊的 issue 应恰好带有一个类别角色和一个状态角色。如果状态角色相互冲突，先标记出来并询问维护者，然后再做其他任何事。

这些是规范角色名——issue 跟踪器中实际使用的标签字符串可能不同。映射应该已经提供给你——如果没有，请运行 `/setup-matt-pocock-skills`。

状态流转：没有标签的 issue 通常先进入 `needs-triage`；再从这里转入 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 回到 `needs-triage`。维护者可随时覆盖——对看起来异常的流转要标记出来，并在继续前询问。

## 调用

维护者调用 `/triage` 并用自然语言描述想要什么。理解请求并行动。示例：

- “让我看看需要我关注的内容”
- “我们来看看 #42”（issue 或 PR）
- “把 #42 移到 ready-for-agent”
- “有哪些已经可以让代理认领？”

## 展示需要关注的内容

查询 issue 跟踪器，按从旧到新呈现三个桶：

1. **未打标签** — 从未分诊。
2. **`needs-triage`** — 评估进行中。
3. **`needs-info` 且自上次分诊记录以来报告者有新动态** — 需要重新评估。

当 PR 在范围内时，把外部 PR 也纳入这些桶，并给每行标注 `[PR]` 或 `[issue]`。发现环节只呈现*外部* PR（跟踪器配置定义了谁算外部）——协作者进行中的 PR 不属于分诊工作。该过滤仅用于发现；被明确点名的 PR 无论作者是谁都要分诊。

展示每项的数量和一行摘要。让维护者挑选。

## 分诊特定的 issue 或 PR

1. **收集上下文。**通读完整的 issue 或 PR（正文、评论、标签、作者、日期；对 PR 还要读 diff）。解析既有的分诊记录，避免重复询问已解决的问题。使用项目的领域术语表探索代码库，遵守相关区域的 ADR。对照代码库执行两项检查：(a) **冗余**（redundancy）——按领域概念（而不仅是请求的措辞）搜索所请求行为是否已有实现，并报告你查找过的位置。如果找到，那就是“已实现”的 `wontfix`（见步骤 5）。(b) **既往拒绝**（prior rejection）——阅读 `.out-of-scope/*.md`，指出任何与本请求相似的内容。

2. **给出建议。**把你的类别和状态建议连同理由告诉维护者，并附上与请求相关的简要代码库综述——包括是否已实现。等待指示。

3. **验证主张。**在任何拷问之前，先检查主张是否站得住脚。对 bug，按报告者的步骤复现。对 PR，确认 diff 确实做到了它声称的——签出代码，运行相关测试或命令。报告结果：已确认（附代码路径）、复现失败，或细节不足（强烈的 `needs-info` 信号）。经过确认的验证能让代理简报有力得多。

4. **拷问（如需要）。**如果请求需要充实，同时运行 `/grilling` 和 `/domain-modeling` 技能——一轮接一轮地提问把它打磨成型，锐化领域术语，并随着决策落定就地更新 `CONTEXT.md`/ADR。

5. **落实结果：**
   - `ready-for-agent` — 发布一条代理简报评论（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human` — 结构与代理简报相同，但要说明为何无法委派（需要判断取舍、需要外部访问、设计决策、人工测试）。
   - `needs-info` — 发布分诊记录（模板见下）。
   - `wontfix` — 关闭，评论取决于*原因*：
     - **已实现** — 该变更已存在于代码库中。指出它所在的位置；**不要**写入 `.out-of-scope/`（该知识库用于*被拒绝的*请求，而不是已构建的）。
     - **拒绝（bug）** — 礼貌地解释，然后关闭。
     - **拒绝（enhancement）** — 写入 `.out-of-scope/`，在评论中链接它，然后关闭（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage` — 打上该角色。如有部分进展可附一条评论。

## 快速状态覆盖

如果维护者说“把 #42 移到 ready-for-agent”，信任他们并直接打上该角色。先确认你即将做的事（角色变更、评论、关闭），然后行动。跳过拷问。如果未经拷问就移入 `ready-for-agent`，询问他们是否要撰写代理简报。

## Needs-info 模板

```markdown
## 分诊记录

**目前我们已经确认的：**

- 要点 1
- 要点 2

**我们仍需要你（@报告者）提供的：**

- 问题 1
- 问题 2
```

把拷问过程中解决的所有内容都记录在“目前我们已经确认的”之下，让这些工作不致丢失。问题必须具体且可操作，而不是“请提供更多信息”。

## 恢复之前的会话

如果 issue 或 PR 上已有分诊记录，先阅读它们，检查报告者是否已回答了未决问题，并在继续之前呈现更新后的全貌。不要重复询问已解决的问题。
