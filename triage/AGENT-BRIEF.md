# 撰写代理简报

代理简报（agent brief）是当 GitHub issue 或 PR 转入 `ready-for-agent` 时发布的一条结构化评论。它是 AFK 代理将要依据的权威规格。原始正文和讨论只是上下文——代理简报才是契约。

简报陈述**代理应该做什么**，这一点对两种载体都适用：对 issue，是从零构建该变更；对 PR，则是*针对现有 diff* 还剩什么要做——完成它、补齐缺口、回应评审意见。两种情况原则相同；下方的 PR 示例展示了差异。

## 原则

### 持久性优先于精确性

issue 可能在 `ready-for-agent` 中停留数天或数周。期间代码库会发生变化。撰写简报时要让它即使文件被重命名、移动或重构后依然有用。

- **要**描述接口、类型和行为契约
- **要**指名代理应查找或修改的具体类型、函数签名或配置形状
- **不要**引用文件路径——它们会过时
- **不要**引用行号
- **不要**假设当前的实现结构会保持不变

### 描述行为，而非步骤

描述系统**应该做什么**，而不是**如何**实现。代理会重新探索代码库并自行做出实现决策。

- **好：**“`SkillConfig` 类型应接受一个类型为 `CronExpression` 的可选 `schedule` 字段”
- **差：**“打开 src/types/skill.ts 并在第 42 行添加一个 schedule 字段”
- **好：**“用户不带参数运行 `/triage` 时，应看到需要关注的 issue 摘要”
- **差：**“在主处理函数里加一个 switch 语句”

### 完整的验收标准

代理需要知道何时算完成。每份代理简报必须有具体、可测试的验收标准。每条标准都应可独立验证。

- **好：**“运行 `gh issue list --label needs-triage` 返回经过初步分类的 issue”
- **差：**“分诊应正常工作”

### 明确的范围边界

说明哪些内容超出范围。这能防止代理过度打磨（gold-plating）或对相邻功能做出假设。

## 模板

```markdown
## 代理简报

**类别：**bug / enhancement
**摘要：**一句话描述需要发生什么

**当前行为：**
描述现在的行为。对 bug 而言，这就是损坏的行为。
对 enhancement 而言，这是该功能所基于的现状。

**期望行为：**
描述代理工作完成后应发生什么。
对边界情况和错误条件要具体。

**关键接口：**
- `TypeName` — 需要改什么以及为什么
- `functionName()` 返回类型 — 当前返回什么 vs 应返回什么
- 配置形状 — 需要哪些新的配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**超出范围：**
- 不应在本 issue 中更改或处理的内容
- 看似相关实则独立的功能
```

## 示例

### 好的代理简报（bug）

```markdown
## 代理简报

**类别：**bug
**摘要：**技能描述截断在单词中间断开，产生损坏的输出

**当前行为：**
当技能描述超过 1024 个字符时，它会在恰好 1024 个字符处被截断，
而不考虑单词边界。这导致描述在单词中间结束
（例如 "Use when the user wants to confi"）。

**期望行为：**
截断应在 1024 个字符之前的最后一个单词边界处断开，
并附加 "..." 以示截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段 — 无需更改类型，
  但填充它的验证/处理逻辑需要尊重单词边界
- 任何读取 SKILL.md frontmatter 并提取描述的函数

**验收标准：**
- [ ] 1024 字符以内的描述保持不变
- [ ] 超过 1024 字符的描述在 1024 字符之前的最后一个单词边界处截断
- [ ] 被截断的描述以 "..." 结尾
- [ ] 包含 "..." 在内的总长度不超过 1024 字符

**超出范围：**
- 更改 1024 字符上限本身
- 多行描述支持
```

### 好的代理简报（enhancement）

```markdown
## 代理简报

**类别：**enhancement
**摘要：**添加 `.out-of-scope/` 目录支持，用于记录被拒绝的功能请求

**当前行为：**
当一个功能请求被拒绝时，issue 会带着 `wontfix` 标签和一条评论被关闭。
决策及其理由没有持久记录。将来类似的请求需要维护者
回忆或搜索以前的讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md` 文件中，
这些文件捕获决策、理由以及请求过该功能的所有 issue 的链接。
分诊新 issue 时，应检查这些文件是否有匹配。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式 — 每个文件应有一个
  `# 概念名` 标题、一行 `**决策：**`、一行 `**理由：**`，
  以及一个带 issue 链接的 `**既往请求：**` 列表
- 分诊工作流应尽早读取所有 `.out-of-scope/*.md` 文件，
  并按概念相似度将新进 issue 与之匹配

**验收标准：**
- [ ] 以 wontfix 关闭功能请求时，会在 `.out-of-scope/` 中创建/更新文件
- [ ] 文件包含决策、理由和指向已关闭 issue 的链接
- [ ] 如果已存在匹配的 `.out-of-scope/` 文件，新 issue 会被
      追加到其“既往请求”列表，而不是创建重复文件
- [ ] 分诊期间会检查现有 `.out-of-scope/` 文件，并在新 issue 匹配既往拒绝时指出

**超出范围：**
- 自动匹配（由人工确认匹配）
- 重新打开先前被拒绝的功能
- bug 报告（只有 enhancement 拒绝才写入 `.out-of-scope/`）
```

### 好的代理简报（PR）

对 PR 而言，“当前行为”描述 diff 的状态，简报要求代理完成或修复它，而不是从零构建。

```markdown
## 代理简报

**类别：**enhancement
**摘要：**完成贡献者为 `triage list` 添加的 `--json` 输出标志

**当前行为：**
该 PR 添加了一个把 issue 列表序列化为 JSON 的 `--json` 标志。正常路径
可以工作，diff 也符合项目的命令结构。还有两个缺口：错误仍以
人类可读文本（而非 JSON）打印，且新标志没有测试覆盖。

**期望行为：**
使用 `--json` 时，所有输出——包括错误——都是 stdout 上格式良好的 JSON，
且命令的退出码不变。标志缺省时，现有的人类可读输出
原样保留。

**关键接口：**
- 命令的错误路径在 `--json` 下应输出 `{ "error": string }`
  而不是纯文本错误
- 复用 PR 已经添加的现有序列化器；不要引入第二个

**验收标准：**
- [ ] `triage list --json` 对成功和错误情形都输出合法 JSON
- [ ] 退出码与非 JSON 命令一致
- [ ] 有一个测试覆盖 `--json` 的成功输出和一个错误情形
- [ ] 默认（非 JSON）输出逐字节保持不变

**超出范围：**
- 给任何其他命令添加 `--json`
- 更改 PR 已定义的成功载荷的 JSON 形状
```

### 差的代理简报

```markdown
## 代理简报

**摘要：**修复分诊的 bug

**要做什么：**
分诊那个东西坏了。看看主文件然后修一下。
150 行附近的那个函数有问题。

**要改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

这很糟糕，因为：

- 没有类别
- 描述含糊（“分诊那个东西坏了”）
- 引用了会过时的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有对当前行为与期望行为的描述
