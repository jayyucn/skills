# 前提事实核查指南

## 诉求拆解

区分：观察 O（实际发生什么）、解释 I（认为原因是什么）、目标 G（希望改变什么）、约束 C（必须满足什么）、方案 S（打算怎么改）。

例：“编辑器卡顿，因为每次输入都保存数据库，应该加防抖。”

- O：输入时卡顿（待复现）
- I：数据库保存导致卡顿（待验证）
- G：输入流畅
- C：不能丢失已输入内容
- S：增加防抖（候选方案）

## 取证顺序

1. **存在性**：诉求说“缺 X”，先搜索 X 是否已在代码、后续 commit、其他 issue 中交付。
2. **时效性**：载体可能是旧快照；尤其核查“某面板已下架”“某能力已移除”等跨议题状态假设。
3. **可复现性**：核查复现步骤、输入、前置状态、环境、测试结果；未复现不等于不存在。
4. **因果性**：区分实际观测与“用户会认为 X 坏了”“代码唯一解释路径”等推测。
5. **隐含约束**：顺路检查载体未写出的手势起点、触发状态、布局依赖、谁让位给谁等。

优先调查低成本且可能直接推翻需求的事实。不要为了简单问题全仓库遍历。

## 证据等级

- **已证实**：有直接观测、测试或可靠代码证据。
- **已证伪**：存在直接反证。
- **未验证**：证据不足；不得用“未复现”冒充证伪。
- **存在争议**：证据冲突或多种解释并存。

报告尽量标明文件路径、行号、用例数、提交信息及证据边界。禁止编造测量、文件位置或测试结果。

## 核查后分流

- 前提已证伪：说明证据，确认剩余问题是否还成立。
- 部分成立：缩小范围，只对剩余诉求溯源。
- 已证实：进入 Why/How 阶梯。
- 不确定：继续可行的取证；无法取证则明确工作假设。
