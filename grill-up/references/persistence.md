# 需求锚点与持久化规范

## 标准产出

- 原始诉求
- 事实状态：已证实 / 已证伪 / 未验证 / 存在争议
- 最小充分需求：一句话描述要实现的结果
- 关键约束：硬约束与重要偏好分开
- 成功条件：如何判断需求满足
- 方案状态：必要条件 / 候选方案 / 已排除
- 未决问题：标记“待决策，勿直接实施”

简单任务可压缩，不强制完整模板。

## 用户确认

当锚点实质改变原始诉求或影响重大决策时，提供：确认并锚定（推荐）/ 需要修正 / 重新溯源。普通澄清不必重复确认。未确认的推断不得写成用户已确认意图。

## 写回位置

只对需要跨会话追踪的决策持久化，优先已有权威载体：

- issue：正文前部放需求锚点、前提核查、约束、成功条件与未决事项；原文保留在后，勿销毁历史证据。标题保持简洁可检索，不强制日期前缀。
- ADR：优先闭合已有对应开放问题，必要时新增决策段。
- 项目上下文/需求文档：放在现有权威位置，避免多份冲突副本。
- 局部代码约束：在合适的注释或测试中固化。
- 多项跨会话追踪：可以新建 issue，关联已有 ADR；单条对话诉求不为形式而新建空 issue。

若有同源 issue，可评论指出共享的决策点，避免重复实施。

## 状态与标签

若仓库已有相应约定：待人裁定用 `ready-for-human`，口径已定且可执行用 `ready-for-agent`。没有此标签体系则不要擅自创建或假定其存在。

## 写入安全

只在具备工具权限且符合用户授权范围时修改载体；重大、不可逆、覆盖历史的操作先确认。优先工具的安全传参接口。复杂 Markdown 通过临时文件及 `--body-file` 等方式传入，避免 shell 对反引号、重定向等字符的解释。

## 交接 grilling

传递：已确认锚点、硬约束、成功条件、未决方案分歧、关键证据。grilling 发现新事实与锚点冲突时可重新进入 grill-up。
