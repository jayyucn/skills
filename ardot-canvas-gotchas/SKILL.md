# Ardot 画布批量编辑：静默失败清单

这些坑的共性是**不报错、结果错**——工具返回 success，画布上却是白的/错的。按此清单逐条规避，可以省掉反复截图排查。

## 一、变量（apply_variables）

### 1. COLOR 值只认 `{r,g,b,a}` 对象，**hex 字符串会被静默写成白色**
```javascript
// ❌ 不报错，但所有引用它的填充都变白色
{"bg": {"type": "COLOR", "value": "#faf9f7"}}
// ✅
{"bg": {"type": "COLOR", "valuesByMode": {"Light": {"r": 0.98, "g": 0.98, "b": 0.97, "a": 1}}}}
```
**症状指纹**：截图上「所有走变量的填充都不见/全白，只有字面色（硬编码 hex）正常」。发现这个症状，第一件事就是 `fetch_variables` 核值。

**注意 hex → 对象要手算**：`#faf9f7` → r=0xfa/255=0.98、g=0xf9/255=0.98、b=0xf7/255=0.97。

### 2. 多模式变量集：`valuesByMode` 的键必须与 `modes` 完全一致
建集时写 `modes:["Light","Dark"]`，之后补值也必须用这两个键（写 `value` 只会落到默认模式）。修正旧集时补上同名 `modes` + `valuesByMode`。

### 2b. 给某个节点切变量模式（做深色稿的正确姿势）
```javascript
U("frameId", {variableModes: [{variableSetId: "3:2", modeId: "3:3"}]})
```
- **必须是数组**，元素形如 `{variableSetId, modeId, libraryKey?}`；写对象（`{"3:2":"3:3"}`）会静默失败（只报一句 potentialIssue）。
- 先 `fetch_variables(nodeId)` 拿到 `availableVariableModes` 里的 set/mode id。
- 于是**深色稿 = 浅色稿的 `C()` 副本 + 一行 variableModes**，零节点改色。这是变量体系最值钱的一次回报。

## 二、填充（fills）

### 3. 变量色 + 同条 fill 的 `opacity` ≠ 半透明
```javascript
// ❌ opacity 被忽略 → 渲染成饱和实色，同色文字被吃掉
fills: [{type: "SOLID", color: "$:Tags:task", opacity: 0.13}]
// ✅ 另建一套半透明色变量（alpha 写进色值里）
fills: [{type: "SOLID", color: "$:TagsSoft:task", opacity: 1}]
```
**症状指纹**：chip / 徽章 / 高亮块是**饱和色块**，里面的文字看不见（文字与背景同色）。

### 4. 渐变 stop 的 `color` **必须是对象**，不能是变量引用字符串
`{color: "$:Colors:accent", position: 0}` 会失败；先算好 hex → `{r,g,b,a}` 对象。

## 三、结构（插入 / 复制 / 移动）

### 5. 实例（INSTANCE）内部不能插入节点
选中节点 id 形如 `3:126;3:27`（含分号）= 实例内的虚拟节点，**插不进去**。三条出路：
- 改**组件本体**（所有实例一起变）；
- 改实例**所在父级**的结构（本次做法：父 frame 由 `horizontal` 改 `vertical` → 新建「内容行」frame 包住原 N 个子节点 → 顶部插新条带）；
- 接受「只在某一实例里加」时，改该实例的**祖先容器**。

### 6. 改父级 `layout` 会污染「随后插入子节点」的尺寸度量
插入时若父级仍是旧 layout，`height: 32` 会被解析成 `fill_container`、宽度退化成默认值（本次退成 720）。
**配方**：① 先 `U(parent, {layout:"vertical"})` ② 再插入 ③ **插入后再 `U` 一次尺寸兜底** `U(newNode, {width:"fill_container", height:32, layoutGrow:0})`。

### 7. 普通帧之间 `C()` 复制的 `descendants` 覆盖**静默无效**
`C("src", parent, {descendants: {"id": {content:"x"}}})` 不报错但不生效；事后的 `U(复制体+";"+原子ID, ...)` 也定位不到。
→ **行数不多时直接 `I()` 重建**，别在复制+覆盖上耗时间。

### 8. `M(node, parent, index)` 的 index 在普通帧上不可靠
实测：移到 index 5 落在 4、移到 8 被 clamp 到 6。要精确顺序时用**删净重插**：
1. `D()` 掉所有错位节点；
2. 按目标顺序依次 `I()`（插入恒 append 到末尾 → 插入顺序就是最终顺序）；
3. `batch_read(parentId, readDepth:1)` **只读校验** children 顺序。

## 四、度量与验证

### 9. 文本固定宽要先减父级 padding，否则报溢出
表格卡：宽 860，父级 padding 32×2 + stroke → 可用约 796。列宽总和超了会返回 `potentialIssues`（文本溢出 40px 这类）。**先算可用宽再定列宽**，并把列宽写进设计备注，方便下一张稿复用。

### 10. 截图是 URL，要 curl 下来再 Read；且是稀缺资源
- `capture_screenshot` 返回的是 URL 列表，必须 `curl -s -o <本地路径> <url>` 再 `Read` 才能看到图。
- 配额：一个**修复批次**最多 1–2 次。先跑 `capture_layout(problemsOnly:true)` 找结构问题（免费且信息密度高），把一批修复全做完再截图验收。
- 截图会缩放到约 75%（1440 → 1080），细节判断要按比例换算。

## 五、让「同一批稿」保持一致

- 屏幕级 chrome（窗口标题栏、状态条）与侧栏这类**多稿共用**的元素，尽量做成 **reusable 组件**；做不了组件（如标题栏每稿标题不同）就**固定一套参数复制**（高 32 / 底色 sidebar / 三按钮 44×26 / 图标 1.4px 线稿），并把参数写进备注。
- token 一律走画布变量（Light/Dark 双模式），深色稿靠**切模式**产出，不要逐节点改色——否则字体/边框/语义色会漂移。

## 六、空「占位」frame 的陷阱（复制后爆发）

横向排版里常放一个空的「占位」frame（`layoutGrow: 1` + `width: fill_container`）来把右侧元素推到右边。**它在原稿里正常，但被 `C()` 复制后会拿到继承高度**——表现为某个标题行突然高 100+px、下方内容被挤出画布。

**配方（两条一起上）**：
1. 建占位时就写 `height: 0`（而不是 `hug_contents`），别给它机会被拉伸；
2. 复制/大改之后跑一次 `capture_layout(problemsOnly:false, maxDepth:1)`，**逐个核对子节点高度**（标题行应为 28–40，出现 116 这种值就是它），把占位统一 `U(id, {height: 0})`。

诊断口诀：**「某一行莫名很高，先看它里面的空占位」。**

## 七、往里插「中间位置」的一整块：用 append 顺序倒推

想把已存在的整块结构（如把 A 页的「字段定义卡」搬到 B 页的中间）插入到指定位置时，`M(node, parent, index)` 的 index 不可靠，但 **`I()`/`C()` 恒 append 到末尾**是可靠的。于是：

```
目标顺序：[头, 副标, 字段块, 标题行, 看板]
1) C(源字段块, parent)          → 顺序：头, 副标, 标题行, 看板, 字段块
2) C(现有标题行, parent)         → ... 字段块, 标题行副本
3) C(现有看板, parent)           → ... 字段块, 标题行副本, 看板副本
4) D(原标题行), D(原看板)         → 头, 副标, 字段块, 标题行副本, 看板副本 ✓
```
即「复制需要的 + 复制要往后挪的 + 删掉原位」= 一次拿到目标顺序，不需要任何 index。

**推论（重排「容器自己的 children」）：整容器删了重建，比逐个 `M()` 挪子项省。** 要改的是一个已有容器内部的顺序 / 分组（典型：把扁平列表改成「分组头 + 组内项」两级），直接 `D(容器Id)` 再按目标顺序 `I()` 重建——子节点随容器一起删干净，插入顺序即最终顺序。只是容器内的文字要重打（`I()` 建的是新节点，内容得再写一遍），所以卡片越小越划算。本次 09 稿左栏「标签列表卡」由扁平 6 项改成「内建标签 / 我的标签」两组就是这样两批 ops 做完的。

**推论 2（副本内部 id 全新，事后改不了）：** `C()` 产出的副本，**整棵子树的 id 都是新的**。所以「先复制、再按原 id 去改副本内部」必然失败——`I("旧子id", …)` 只会在响应里给一条 `potentialIssues: ["Insert: parent not found"]`（不抛错、不中断其余 ops），`U("旧子id", …)` 更可能静默无效。要用副本内部就必须先 `batch_read` 副本自己拿 id。**顺序修正的正确姿势**：先 `I()` 新建要插在前面的块 → 再 `C()` 复制「需要后移的」节点（append 到末尾）→ 最后 `D()` 原位。本次 02 稿详情栏（删字段定义段 + 指标行插到表格之前）就是一次「建新块 → C 挪位 → D 原位」拿到的正确顺序；反过来做（先复制、后想改副本）就掉进这个坑。

**附带铁律：复制源 id 必须先核对。** 同名的块（多张稿都有「字段定义卡」）id 极易记混——本次就把 04 稿的卡复制进了 03 稿，结果 03 里出现了「阻塞于 / 继承自 #任务」的字段定义。跨稿复用前先 `batch_read` 看一眼源节点的子节点名再复制。

**推论 3（跨稿同步形态：C 与 I 的分工）：** 把 A 稿的形态搬到 B 稿时，按「这段要不要改里面的字」二选一——
- **不用改内容** → 直接 `C(源段, 目标父)`；定位靠父级对齐，例如详情头要「标题在左、视图切换在右」= `U(父, {primaryAxisAlignItems:"SPACE_BETWEEN"})` + `C(视图切换段, 父)`，一次到位、零重建。
- **要改内容** → `I()` 重建（`C` 出来的子树 id 全新，改不了，见推论 2）。
同一次同步里两种混用是常态：本次 04 稿同步 02 形态 = 视图切换 `C`（不改字）+ 指标行/工具行 `I`（要改数字与文案），再用 `M(末尾旧段, 父)` 把原有的表格复位到最后。
**顺带技巧**：横向 auto-layout 里最后一列若为定宽文本，末尾会留一段空白——把它改 `width: "fill_container"` 即自动吸收余宽（表头与各行的同一列都要改）。

## 八、实例（INSTANCE）内的「覆盖」与「新增」

### 11. 组件本体新增节点 → 所有实例自动长出同名节点，寻址用「实例ID;组件内新ID」
在组件里 `I(组件内某父级, {...})` 得到组件内 id `A`，则任一实例 `Ix` 中对应节点是 **`Ix;A`**（多级 `Ix;A;B` 同理）。这是**唯一**能让「9 张稿的侧栏同时多一个入口」的省力路径——改一次组件，全稿同步。
（配套限制：实例内**不能** `I()` 插节点，只能改组件本体或实例的祖先容器，见第 5 条。）

### 12. 实例内改填充：`fill: "#hex"` 简写能用，`fills: [...]` 两种写法都不能用
```javascript
U("3:1255;3:42", {fills: [{type:"SOLID", color:"#EDE8E0"}]})         // ❌ Expected object at [0].color, but received 'string'
U("3:1255;3:42", {fills: [{type:"SOLID", color:{r:0.93,g:0.91,b:0.88,a:1}}]}) // ❌ Unrecognized key(s): 'a' at [0].color
U("3:1255;3:42", {fill: "#EDE8E0"})                                   // ✅ 生效
U("3:1255;3:34", {fills: []})                                        // ✅ 清空填充同样只用简写形态
```
结论：**实例覆盖一律用 `fill` 简写 + 字面 hex**（与第 3 条一致——实例覆盖不认变量引用）。代价是丢掉了 Dark 模式自动跟随，因此实例级覆盖只用于「当前态高亮」这类局部意图；大面积配色仍应回到组件本体 + 变量。
`potentialIssues` 里这三条报错**不影响同批其它 op**，但会被要求先修——所以别把实例覆盖和「必须在同批完成」的插入混在一起。
