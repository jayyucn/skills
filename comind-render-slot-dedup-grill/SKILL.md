# 渲染位存废的拷问配方

## 症状

用户指着某段模板问「有没有必要保留」。字面是布局取舍，实际往往藏着数据层缺陷。

## 铁律：先证明重复，再问存废

**别直接回答「留 or 删」。** 先取证这两件事：

1. **同一份数据是否被两个渲染位消费？** → 找出两处各自的**筛选谓词**，逐项比对，而不是比对渲染结果。
2. **删任一侧能否消解重复？** 多数不能——只是把可见性转移到别处。

## 取证步骤

1. **列出该数据的所有渲染位**。`BlockTagFields` 用 `variant` 枚举；一般从模板里grep 同一 prop /同一 store 派生值的消费点。
2. **逐位写出筛选谓词的源码位置**（`file:line`），格式化成可比对的两列表。
   实例（本次）：
   | 渲染位 | 谓词 | 语义 |
   |---|---|---|
   | `chips` 行尾 | `bottom-of-block` 内置 + `!isSystemField`（全部自定义） | **有值才显示**（速览） |
   | `list` 下方字段区 | 标签有效字段并集 − `between-bullet-content` | **模板内即显示**（引导填写） |
3. **谓词差异即重复的来源**。语义不同（有值 vs 模板内）时，强行对齐会牺牲其中一方 ⇒ 别用「扩展去重逻辑」掩盖。
4. **回查历史 ADR 是否已定过方案但未实施**。`block_display` / `blockDisplay` 在 `src/` `crates/` 全仓无落点 ⇒ 该去重是「已决策未实施」，重复是实况而非设计。
5. **注意恒空渲染位**：`inlineRows` 的 `.filter()` 可能把某槽的字段全排空。逐个验证「该 displayPosition 值在全仓是否还有第二个字段」——只有 priority 一个 ⇒ 该槽恒空，属零行为变化的独立清理项。

## 判据：单一权威展示位

把本质需求钉成**不变量**，而非「保留/删除」：

> 同一份数据在同一实体上，有且只有一个权威展示位。

反证检验：换一个完全不同的方案（删A / 删 B / 都不删只改筛选）能否满足同一目标？都能满足「不出现两个源」但代价各异 ⇒ 不变量提炼正确。「少一个渲染位」则不满足反证（它碰巧同时解决了两者）。

## 输出

- 本质需求一句话 + 阶梯 + 反证，作为**确认题**（AskUserQuestion）让用户锚定。
- 回写**该决策的权威载体**（此处是 `docs/adr/0050-*.md` 新增 D 段），不要新开 issue 走形式。
- 未定的归属侧写成「待定项（勿直接实施，需先压力测试）」，交下游 grilling。

## ADR 写作铁律（自检）

新增段落后必须 grep 自查，命中即改写为中性决策语言：
`grill|设计稿|用户|裁定|推翻|原稿|截图|锚定`
（例：「grill-up 锚定 2026-10-04」→「字段值单一权威展示位」；「待裁定」→「待定项」）

另：改 ADR 前先验换行符（`open(f,'rb').read().count(b'\r\n')`），LF 文件被 Edit 写成 CRLF 会污染整文件 diff；写完再验一次。

## 回写载体：先查 D 编号占用

ADR 决策段用 `D<n>` 编号，**编号是全 ADR 唯一的**，且代码注释里广泛引用（如
`src/utils/field-hide.ts:2` 写 `ADR-0050 D18`）。新写决策段前必做三查：

```bash
grep -n "D18\|D19" docs/adr/0050-*.md | head          # ① 该 ADR 内已用编号
grep -rn "ADR-0050 D18" src/ --include=*.vue --include=*.ts   # ② 代码里的引用
grep -rn "D18" src/ | head                # ③ 别处是否已占号
```

2026-10-04 实测踩中：新写的「字段值单一权威展示位」占了 D18，而 **D18 已被既有的「隐藏规则」
决策占用**（10 处代码引用），改回D19 后须同步修正 ADR 内交叉引用（`见 D18 后果 / 待办` → D19）。

## 实施前置核查：目标列可能已存在

D17 要求「新增 `block_display` 列」，但先查同语义的列是否已落地 —— `hide_when` 已是
**Rust 持久化的定义级展示控制列**，取值表含 `always`（=永不展示），且**双存储路径齐备**
（native `storage/sqlite.rs` CREATE TABLE + 迁移；wasm `storage/sqljs.rs` CREATE TABLE +
迁移 + SELECT/INSERT/UPDATE；按 `comind-core-add-column` 清单逐项验过）。则新列的必要性需重估为三选一：

1. 复用既有列（零 schema 变更），代价 = 语义叠加、取值空间被占；
2. 新增列（原案），代价 = 走 `comind-core-add-column` 全流程；
3. **先只做去重，展示配置暂缓** —— 去重本身不依赖任何 schema 变更。

**判据**：诉求是「消除重复」还是「加一个可配置项」？后者才需要新列。别把两件事捆成一次schema 变更。

## 实施：清一个渲染位前 grep 全仓调用点

判「该槽恒空」时，`variant="right"` 这类 prop 的消费点**通常不止被问的那一个文件**。
实例：`index.vue` 与 `Backlinks.vue` 都挂了 `variant="right"`，只改前者会留下恒空容器。
一次 grep 收全：

```bash
grep -rn "variant=\"right\"\|'right'" src/ --include=*.vue | grep -v test
```

连带要清：prop 联合类型的成员、模板 `v-if` 分支、**因该分支恒假而永不可见的元素**
（本次 `variant === 'right' && hoveredId === fv.id` 的删除按钮）、以及仅为该分支存在的中间层
（`inlineRows` 本只是 `betweenRows` 加 right 分支的别名 → 合并成一个）。

## 假绿：新测试必须做「回退实现 ⇒ 该例转红」

**绿测试可能什么都没锁。** 断言若只依赖未改动的旁支逻辑，缺陷态下照样绿。
实例：断言「chips 不含自定义字段」——那只取决于 `displayRows` 口径，与本次去重无关，绿得毫无意义。

```bash
cp <file> /tmp/x.bak                      # 备份
# 把实现回退到缺陷态（去掉刚加的那行条件）
npx vitest run <test>                     # 该例必须转红，否则测试无效
cp /tmp/x.bak <file>                      # 恢复并复验绿
```

判据：**回退后转红的例数 == 新增的去重断言数**。对不上就是有假绿，要重写。

## 归因：既存红用「单文件 checkout 对照实验」，不用 stash

判定「这些红是不是我引入的」时，把**自己改过的文件**逐个 `git checkout HEAD -- <file>` 回到
未改状态跑同一批测试：

- 结果仍红 ⇒ 既存基线，与本次无关。
- 记得改回来（`cp /tmp/*.bak` 或重新应用改动）并复验。

`git checkout HEAD -- <单文件>` 在安全白名单内；**`git stash` 是铁律禁区**。
另可先用 `grep -c "MyComponent" <失败测试文件>` 排零直接依赖，再做对照实验确认间接依赖。

## 别把「去重」做成枚举分类 —— 问自定义字段怎么办

**踩过的坑（2026-10-04 两次）**：第一次按 `displayPosition` 枚举分类去重（内联槽 / 底部 / 自定义），
看似完备，实测**自定义字段仍双现**。根因是两处谓词**分类维度不同**：

| 渲染位 | 谓词 | 收哪些 |
|---|---|---|
| 行尾 chips | `bottom-of-block` \|\| `!isSystemField(key)` | 域字段 + **全部自定义** |
| 下方字段区 | 模板并集 − 枚举掉的 position | 模板内全部 |

自定义字段落在**两边交集内**。判据：**枚举法只对「穷举且互斥」的分类有效**；一旦存在
「无声明的默认类」（自定义字段），它必然同时落进「兜底收」与「兜底不排」两侧。

**正确问法**：不是「哪些已被别处渲染」，而是「**这个字段有没有行内渲染位**」——
按渲染位反查，而非按字段分类反查。

## 顺带查「数据源不一致」—— 同一字段两种标题形态

删/改一个渲染位时，问「它读的定义来源和别处一致吗」。踩坑实例：`defOf` 只查系统 seed 派生的
`BUILT_IN_FIELDS`（编译期常量），自定义字段查不到 ⇒ `titleOf(key) ?? key` 回退显示
**field id**；而下方字段区读 `tagsStore` 持久化定义 ⇒ 同一字段一个显示 `f-muov2k…`、一个显示
`分类`。**这类缺陷比重复更隐蔽**：它不报错、测试照绿，只在真实数据上显形。

判定：凡渲染侧出现 `?? key` / `?? id` 之类的回退，就去查有没有更权威的定义来源可查
（store / RPC / 持久化表）。

## 删渲染位时，守卫选择器要逐支验证仍有效

`SELF_INTERACTIVE_SELECTOR` 这类「元素类名守卫」里，**每个分支对应一个渲染位**。删掉某个
渲染位只让该分支失效，其余分支**仍然有效**（实例：删行内 chips 后 `.property-item` 仍由
`all` 变体产出、`.property-inline-item` 仍由 `between` 槽产出）⇒ **不要顺手删选择器里的类名**。

连带的是**测试锚点失效**：以被删渲染位为锚的用例会转红。改锚原则 = **验同一条不变量**，
不是找一个「也在这块区域内」的元素。实例：块内容区 `.block-content` 虽在块内，但**它本身
要接Ctrl+Click 切块**，不属自交互元素，换锚等于换了一条不变量（改后仍红）。正解是锚到
守卫选择器内**仍然存在**的分支元素。
